# GridPool V2.2 Coordinated Cutover

Status: scheduled for Bitcoin block-height activation. V2.2-capable nodes run
V2.1 consensus until mainnet-beta height `959500`, then activate V2.2 together.

## Ships In Version 22

- CONS-020: deterministic Monotonic Snapshot Reconciliation for fully validated
  sibling boundary reserves, with block-hash family isolation and bounded
  member retention.
- CONS-001: new previous-parent proofs received by direct ingress after the
  local boundary cannot enter the canonical unpaid reserve. Already-known
  pre-boundary lineage remains usable.
- CONS-002: paid-once removal is keyed to the payout snapshot proven by the
  winning block coinbase context, including cross-snapshot payment.
- CONS-005 status: one-block competing-boundary family restoration is covered.
  Two-block replay and paid-confirmation rollback vectors remain follow-up work.

## Does Not Ship

- CONS-003 human fee decision is **resolved** (2026-07-19): public reference
  network is support-on only; cross-variant consensus deferred. Remaining work is
  implementation/docs enforcement, not product choice.
- CONS-010 peer-header snapshot activation remains deferred. A peer header may
  provisionally freeze work under existing policy but does not activate a V2.2
  payout snapshot.

## Compatibility And Rollout

The mainnet-beta activation height is `959500`, estimated for approximately 24
July 2026 from the 19 July tip. `boot_protocol_version` remains the binary's
configured maximum capability. `v22_activation_block_height` selects the
consensus activation height: mainnet sample configuration uses `959500`, while
the testnet4 lab sample uses `0` for immediate activation. Zero is only for
tests or an explicitly isolated lab and is rejected for production mainnet.

Before height `959500`, upgraded nodes advertise active consensus `21`, use
state-bundle schema `2`, follow V2.1 state rules, and peer with legacy V2.1
nodes. At and above the height they advertise active consensus `22`, use schema
`3`, and perform MSR only for explicit, fully validated family members. Legacy
nodes then become incompatible as expected; there is no soft merge of V2.1 and
V2.2 rules after activation. Status exposes software consensus capability,
active consensus, activation height, and blocks remaining.

Activation uses the persisted local Bitcoin tip already trusted for snapshot
boundaries and mining templates. A provisional peer header cannot activate
V2.2. If the trusted tip height is unknown, a non-zero schedule fails closed to
V2.1 rather than activating early.

## Operator Procedure

1. Upgrade every participating node several blocks before height `959500` and
   back up its data directory and current image/commit.
2. Verify status reports software capability `22`, active consensus `21`,
   activation height `959500`, and the expected blocks remaining. Confirm V2.1
   peers remain compatible during this window.
3. At height `959500`, verify active consensus changes to `22`, schema changes
   to `3`, upgraded peers reconnect as compatible, and reconciliation counters
   remain healthy.
4. Roll back the binary only before activation. After activation, remain on a
   V2.2-capable build or follow a separately coordinated recovery plan; a V2.1
   rollback is consensus-incompatible.

Keep outsider hash contribution at or below 10% until the V2.2 soak completes.
Simulation results informed this cutover but are not a security guarantee.
